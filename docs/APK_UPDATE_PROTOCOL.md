# Mandatory Android APK update protocol

JoJo Android clients must never continue normal operation when the hub requires a newer app version.

## Ownership

- `jojos-base` decides which app version is desired/required for a store or fleet.
- `jojos-hub` caches APK artifacts locally and exposes the version/update contract over the store LAN.
- `jojos-kso` and `jojos-kitchen` compare their installed `versionCode` with the hub contract.

Android clients must not download production APKs directly from GitHub. The hub is the local distribution point so updates continue to work even when store devices have no Internet access.

## Hub release storage

KSO:

`/home/admini/jojos-releases/kso/jojos-kso-latest.apk`

Kitchen:

`/home/admini/jojos-releases/kitchen/jojos-kitchen-latest.apk`

Each release directory should also contain metadata generated by deployment:

- `version.json`
- `*.sha256`

Suggested `version.json`:

```json
{
  "app": "kitchen",
  "version_code": 14,
  "version_name": "0.14.0",
  "min_supported_version_code": 14,
  "mandatory": true,
  "sha256": "...",
  "size_bytes": 12345678,
  "published_at": "2026-08-08T12:00:00Z"
}
```

## Hub API

Provide a local endpoint per app role:

`GET /api/apps/{app}/version`

where `{app}` is `kso` or `kitchen`.

Example response:

```json
{
  "app": "kitchen",
  "version_code": 14,
  "version_name": "0.14.0",
  "min_supported_version_code": 14,
  "mandatory": true,
  "apk_url": "/api/apps/kitchen/apk",
  "sha256": "...",
  "size_bytes": 12345678,
  "published_at": "2026-08-08T12:00:00Z"
}
```

APK download endpoint:

`GET /api/apps/{app}/apk`

The hub must serve the exact cached APK represented by the metadata and return a stable checksum/ETag where practical.

## Client decision

At app startup, before entering normal business UI:

1. Read the installed Android `versionCode`.
2. Call `GET /api/apps/{app}/version` on the local hub.
3. If installed version is lower than `min_supported_version_code`, enter **MANDATORY_UPDATE** state.
4. If installed version is lower than `version_code` and `mandatory=true`, enter **MANDATORY_UPDATE** state.
5. Otherwise continue normal startup.

The client must also re-check periodically and after reconnecting to the hub so a long-running kiosk cannot remain indefinitely on a blocked version.

## Mandatory update UX

When in `MANDATORY_UPDATE` state:

- hide/disable all normal KSO/Kitchen functionality;
- show current and required version;
- show download/install progress;
- provide no `Skip`, `Later`, back navigation or bypass action;
- retry automatically after transient download failures;
- after installation/restart, repeat the version check before opening the normal UI.

If the hub is reachable but the required APK is missing/corrupt, keep the app blocked and show a service/admin error state. Never fall through into normal operation on a version explicitly marked unsupported.

## Download integrity

Before installation:

1. download APK to app-private/cache storage;
2. calculate SHA-256;
3. compare with hub `sha256` metadata;
4. reject and re-download if it does not match.

The package name and signing certificate must also match the installed application. Production builds must always be signed with the same protected release key.

## Installation modes

### Preferred production mode

Devices are provisioned as dedicated/kiosk managed Android devices (Device Owner / OEM management). Use an approved managed installer/PackageInstaller flow so the update can complete without ordinary user interaction where the device policy/OEM supports it.

### Fallback mode

If the device is not provisioned with silent-install capability, Android may require the system package installer confirmation screen. In that case JoJo still enforces the update by keeping the business UI blocked until the new version is installed successfully.

The application itself cannot bypass Android package-install security restrictions on an unmanaged device.

## Rollout control

`jojos-base` should later support:

- desired version per app (`kso`, `kitchen`);
- minimum supported version;
- mandatory flag;
- fleet-wide or store-specific rollout;
- rollout status by hub/store/device;
- ability to pause a bad release;
- ability to point a hub back to a previous signed release where rollback is supported.

The hub should cache at least the current and previous known-good release so rollback does not depend on Internet availability.
